# Story: Optimize Cache Hit Mission Validation Performance (POV)

## 📋 Story Overview

**Status**: ✅ COMPLETE (Implemented 2025-01-06)
**Priority**: P3 - Low (POV optimization)
**Effort**: Small (4-6 hours) - Actual: ~2 hours
**Type**: Performance Optimization (POV Stage)

> **POV SCOPE**: This is a proof-of-value optimization. Focus on demonstrating the pattern works, not production-grade implementation. Skip extensive testing and benchmarking.

> **✅ ALIGNED**: This optimization maintains transaction atomicity. All operations remain inlined within the parent mutation as documented in `docs/convex-howtos/transaction-atomicity.md`.

### Problem Statement

On every cache hit, the system runs mission validation (query + mutation) even though the command output is cached. This results in O(N) database operations where N = number of active missions.

**Current Performance**:

- 0 missions: ~4 DB operations, 50-100ms
- 1-2 missions: ~6-8 DB operations, 100-200ms
- 10 missions: ~24 DB operations, 300-500ms

### Why This Matters

1. **User Experience**: Cache hits should be instant, but can take 300-500ms with many missions
2. **Scalability**: Performance degrades linearly with mission count
3. **Database Load**: Unnecessary queries/mutations on cache hits

### Why Mission Validation Can't Be Cached

Mission validation state **cannot** be cached because:

1. Mission progress is independent of game state (room, health, threats)
2. Mission validation has side effects (updates progress, awards points)
3. Same command can advance different missions at different times
4. Would require complex invalidation logic

**Current behavior is correct by design** - this story is about optimization, not fixing a bug.

### Design Principle: Minimize Cache Hit Side Effects

**Current cache hit operations** (`gameActions.ts:106-142`):

1. ✅ Mission validation - NECESSARY (game progression)
2. ✅ Terminal output insert - NECESSARY (player sees output)
3. ✅ Game state update - NECESSARY (skill points, session)
4. ⚠️ Cache hit counter - DEBATABLE (analytics only)

**Note**: The cache hit counter question is out of scope for this optimization story. If analytics overhead becomes a concern, create a separate ticket to evaluate async analytics patterns.

## 💡 Proposed Solution

### Option 1: Batch Mission Validation (Recommended)

> **✅ ATOMICITY COMPLIANT**: This optimization maintains atomicity by keeping all operations within the parent mutation. No `ctx.runMutation` calls are introduced.

**Current Implementation** (`convex/missions.ts:218-250`):

```typescript
// ✅ CORRECT - Already atomic (inline operations)
// But inefficient: N separate queries + N patches within same transaction
for (const missionId of missionIds) {
  const result = await validateMissionStepInternal(ctx, playerId, missionId, playerCommand);
  // Each call performs: 1 query (get mission progress) + 1 patch (update progress)
}
```

**Optimized Implementation**:

```typescript
// ✅ CORRECT - Still atomic, just more efficient
// Single query + in-memory validation + sequential patches within same transaction
const allProgress = await ctx.db
  .query("missionProgress")
  .withIndex("by_player_status", (q) =>
    q.eq("playerId", playerId).eq("status", "in_progress"),
  )
  .collect();

// Validate all in memory (no DB operations)
// Note: validateAndPrepareUpdate is the pure validation function from Phase 1
const updates = allProgress.map(progress =>
  validateAndPrepareUpdate(progress, playerCommand)
);

// Apply all patches sequentially within the same mutation transaction
// All operations occur atomically - if any patch fails, entire transaction rolls back
for (const update of updates) {
  if (update.changes) {
    // Only patch if validation determined changes are needed
    await ctx.db.patch(update.id, update.changes);
  }
}
```

**Benefits**:

- ✅ Maintains true atomicity (all operations in same transaction)
- **Before**: N separate queries + N patches
- **After**: 1 query + N patches (still within same transaction)
- Better Convex transaction semantics
- Maintains correctness
- Cleaner error handling (automatic transaction rollback)

**Effort**: Medium - Requires refactoring `validateMissionStepInternal`

**Key Principle**: This is a **performance optimization within an atomic transaction**, not a change to transaction boundaries. All operations remain inline within the parent mutation.

## 🔧 Implementation Plan (POV - Lean Approach)

### Phase 1: Implement Batch Validation (2-3 hours)

1. **Extract pure validation function**
   - Create `validateAndPrepareUpdate(progress, command)` - no DB access
   - Takes a `missionProgress` document and player command
   - Returns `{ id: Id<"missionProgress">, changes: Partial<Doc<"missionProgress">> | null }`
   - Pure function: no side effects
   - This is the function referenced in the optimized implementation (line 98)

2. **Create batch validation function**
   - `validateAllMissionsInBatch(ctx, playerId, command)`
   - Single query for all active missions
   - Call `validateAndPrepareUpdate()` for each mission in memory
   - Loop through updates with `ctx.db.patch()` for each change
   - All operations remain inline within the same transaction

### Phase 2: Integration & Testing (2-3 hours)

   - Verify mission progression still works
   - Confirm cache hits work correctly

3. **Basic validation**
   - Check Convex dashboard for operation count reduction

## 📊 Expected Impact

### Performance Improvements

| Active Missions | Current Ops | Optimized Ops | Latency Improvement |
|----------------|-------------|---------------|---------------------|
| 0              | 4           | 4             | 0% (already fast)   |
| 1              | 6           | 5             | ~15%                |
| 2              | 8           | 5             | ~40%                |
| 5              | 14          | 5             | ~65%                |
| 10             | 24          | 5             | ~80%                |

**Key Optimization**: Reduces N separate mission queries to 1 batch query, while maintaining the same number of patches (N) within a single atomic transaction.

### Database Load Reduction

- **Before**: N separate queries (1 per mission) + N patches per cache hit
- **After**: 1 batch query + N patches per cache hit (all in same transaction)
- **Query Optimization**: O(N) read queries → O(1) read query
- **Patch Operations**: N patches remain (sequential within atomic transaction)
- **Overall Complexity**: O(N) total operations, but with reduced overhead from single query
